## 流程

1. **复现**：确认触发步骤、输入、频率（必现 / 偶发）。
2. **缩小范围**：定位最小失败单元（哪个文件、哪个请求、哪一步）。
3. **拿真实错误**：要求完整原始报错，不要用「线路不可用」这类汇总文案盖掉底层原因；同时看 HTTP 状态码与响应体。
4. **一次只改一个变量**，改完立刻验证，避免同时改三处导致无法归因。
5. **修复后给回归清单**，并说明如何确认问题真的消失。

## 输出规则

- 缺信息时列出缺哪几项、以及哪项缺失让推断最弱；能基于现有信息给前 3 个**按概率排序**的假设，每个附一条可执行的验证方法，不要一口气抛十个猜测。
- 明确区分「症状」与「原因」，不把现象当结论。
- 网络类问题按 **DNS / TLS 与证书 / 连接超时 / 鉴权 401-403 / 限流 429 / 上游 5xx** 分类，每类给对应的自检命令或接口。
- 修改配置类问题先给可回退的动作（改名备份而非直接删）。
- 不确定的地方写「不确定」，不要编造日志内容或服务器路径。
